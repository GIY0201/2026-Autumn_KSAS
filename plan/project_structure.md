## 3. 파일 배치 원칙

| 위치 | 담당 내용 | 두지 않는 것 |
|---|---|---|
| `data_generation/<version>/` | 데이터 생성 코드, 해당 버전의 설정·테스트 | 실제 원본 자료, 생성 데이터 |
| `models/<model_name>/<version>/` | 해당 모델의 학습·추론·평가 코드, 설정·테스트 | checkpoint, 예측 결과, 평가 결과 |
| `visualization/<version>/` | 궤적 재생·비교·표시 코드, 설정·테스트 | 내보낸 이미지·영상·보고서 |
| `contracts/<version>/` | 모듈 간 공통 입출력 형식·단위·시간축 규칙 | 모델별 내부 구현, 기체별 임의 성능값 |
| `data_sources/<source_id>/` | 출처·기체별 외부 원본과 출처 설명 | 원본을 덮어쓴 가공 결과 |
| `outputs/` | 생성 데이터, 학습·평가·시각화 결과 | 기능 구현 코드 |
| `plan/` | 합의된 계획, 설계 문서, 설명용 도식 | 대량 실행 결과, 임시 실험 코드 |
| `temp/` | 해당 작업에만 필요한 임시 파일 | 원본 자료, 최종 결과의 유일한 사본 |

`<version>`, `<source_id>`, `<dataset_id>`, `<run_id>`는 경로 설명용 표기입니다. 실제 이름으로 된 빈 예제 폴더는 미리 만들지 않습니다.

## 4. 버전 관리 규칙

1. 데이터 생성·모델·시각화·공통 형식의 버전은 각각 독립적입니다. 번호를 일괄 증가시키지 않습니다.
2. 모델 종류와 버전은 분리합니다. 다른 모델의 추가는 `models/<model_name>/v1/`이며 GRU의 후속 버전으로 취급하지 않습니다.
3. 개발 중인 버전은 수정할 수 있습니다. 비교 기준으로 확정한 버전은 보존하고, 이후 동작이나 의미를 바꾸는 수정은 다음 버전에서 진행합니다.
4. 같은 코드에서 seed·학습률 등 실행 설정만 바뀌면 새 코드 버전 대신 새 실행 ID를 사용합니다.
5. 아직 도입하지 않은 `v2`나 다른 모델 폴더는 미리 만들지 않습니다. 폴더가 있다고 검증된 버전으로 표시하지 않습니다.
6. `final`, `final2`, `수정본`, `최종_진짜` 같은 이름을 사용하지 않습니다. 실행 시 버전을 명시하고, 자동으로 최신 버전을 선택하지 않습니다.
7. 이 규칙은 현재 문서 규칙입니다. 버전 고정이나 덮어쓰기 방지를 강제하는 프로그램은 아직 없습니다.

## 5. 향후 결과물 배치와 추적

향후 실행할 때 다음 위치를 사용합니다.

- 생성 데이터: `outputs/data_generation/<version>/<dataset_id>/`
- 학습·평가 결과: `outputs/models/<model_name>/<version>/<run_id>/`
- 시각화 결과: `outputs/visualization/<version>/<run_id>/`

같은 버전을 반복 실행해도 새 ID로 구분하며 기존 결과를 덮어쓰지 않습니다. 모델 실행 폴더에는 checkpoint와 해당 평가 결과를 함께 보관합니다.

각 결과 폴더에는 사용한 코드 버전, 데이터 형식 버전, 입력 데이터 ID, 코드 hash, seed, 실행 설정·환경 기록 위치를 추적할 `manifest.csv`를 둡니다. **구체적인 열 정의, ID 발급 방식, hash 산출 방식과 기록 프로그램은 후속 구현에서 확정**합니다. 이번에는 빈 manifest나 가짜 실행 기록을 만들지 않습니다.

외부 원본의 가공본은 `outputs/`에 두고 원본 경로를 출처로 기록합니다. `configs/`에는 향후 실행 설정을 두되 측정 자료나 대량 생성 결과를 저장하지 않습니다.

## 6. 모듈 연결과 후속 검증

공통 입출력 규칙은 `contracts/`에서 버전별로 관리합니다. Local ENU의 x=East·y=North·z=Up, 위치 m·시간 s, 60초·5 Hz·301개 시점, 생성 표형 데이터 CSV는 이미 합의했습니다. 원점·원본 변환·구체적인 열·관측 입력과 평가용 정답의 파일/접근 경계는 상세화가 필요합니다. [결정 대조표](decision_reconciliation.md), [생성 설계](data_generation_v1_design.md), [모델 인계](model_design_handoff.md)를 함께 확인합니다.

모델과 시각화는 합의된 공개 형식으로 데이터를 읽고 다른 버전의 내부 구현에 직접 의존하지 않도록 합니다. 형식·차원 호환성 판단과 오류 처리 로직은 후속 구현 범위입니다.

이번에 확인할 것은 디렉터리 배치, 문서의 역할 구분, 기존 파일 보존, 실행 코드·결과물 미생성입니다. 다음 항목은 실제 기능 구현 이후에 검증하며 이번 단계에서 통과했다고 주장하지 않습니다.

- 생성 CSV·checkpoint·이미지가 코드 폴더에 저장되지 않는지.
- 같은 버전을 두 번 실행해도 결과가 각각 보존되는지.
- 결과 하나에서 입력 데이터와 사용한 버전·설정을 추적할 수 있는지.
- 지원하지 않는 데이터 형식·차원 조합을 명확히 거부하는지.

## 7. 환경 설정의 보류

`pyproject.toml`과 `uv.lock`은 프로젝트 루트에 둘 예정이지만, 이번 작업에서는 생성하지 않습니다. 실제 Python 환경과 의존성을 결정하는 단계에서 유효한 설정과 lock 파일을 함께 준비합니다.

이 문서는 파일 관리 기준이며 기존 연구 설계나 `AGENTS.md`를 대체하지 않습니다. 새로운 담당 영역이 필요하면 먼저 역할과 배치를 논의합니다.

## 8. 가벼운 폴더별 AGENTS 관리

| 계층 | 파일 | 담을 내용 |
|---|---|---|
| 공통 | 루트 `AGENTS.md` | 독립성·작업 승인·불변 경계·담당 지침 안내 |
| 기능 | 8개 담당 폴더의 `AGENTS.md` | 해당 책임·입출력 경계·금지 사항·먼저 읽을 설계 |
| 현재 버전 | `data_generation/v1/`, `models/gru/v1/`, `visualization/v1/`, `contracts/v1/`의 `AGENTS.md` | X8/GRU/재생/형식에만 해당하는 추가 규칙 |
| 상세 설명 | `plan/*.md` | 설계도·근거·합의/미확정·검증 계획·인계 |
| 실행 안내 | 각 버전 `README.md` | 실제 기능 상태·확인된 실행/테스트 방법 |

1. 모든 지침 이름은 `AGENTS.md`로 통일합니다. 다른 철자의 별도 지침 파일을 만들지 않습니다.
2. 작업 경로의 부모 지침을 먼저 읽고 하위 지침을 추가로 적용합니다. 하위 파일은 공통 불변조건을 무효화하지 않습니다.
3. `configs/`와 `tests/`, 현재 `outputs/`의 하위 경로에는 부모와 중복되는 파일을 만들지 않습니다. 실제로 다른 규칙이 생길 때만 해당 위치에 추가합니다.
4. 여러 모듈을 연결하면 양쪽 담당 지침과 `contracts/AGENTS.md`를 확인합니다. 형식 변경 책임을 한쪽 구현 폴더에 숨기지 않습니다.
5. 상세 수치표·논문 요약·실험 로그는 AGENTS에 누적하지 않고 설계/출처/결과 문서로 연결합니다. 현재 구현 상태가 바뀌면 관련 README와 지침의 상태 문구를 함께 갱신합니다.
